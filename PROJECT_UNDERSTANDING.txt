WHAT IT IS
----------
Class Timer Pro is a Flutter app (package name "class_timer", v1.0.0+5) that
functions as an offline-first academic scheduling assistant for students. It
goes beyond a plain timetable/reminder app by combining:
  - Multiple ways to get a timetable into the app (manual entry, Excel import,
    matrix/grid-style OCR import from photos)
  - Conflict detection between classes/study sessions
  - Notifications with "smart buffer" contextual reminders
  - A Focus Mode for study sessions
  - Gamified productivity tracking (streaks, coins, streak freezes)
  - Academic tools: grade calculator, absence tracker, study planner,
    performance stats, course/program management, timetable explorer

The README.md and logic_and_algorithm.txt describe an ambitious full vision
(AI OCR from photos/PDFs, Google Calendar two-way sync, predictive scheduling
etc.) — these read as a product spec / roadmap. The actual codebase implements
a meaningful subset of this, described below.

TECH STACK
----------
- Flutter, Dart SDK ^3.11.0
- State/data: Provider (declared, though most screens use direct
  StatefulWidget + service calls rather than heavy Provider usage)
- Local storage: Hive + hive_flutter (offline-first persistence), with
  hive_generator/build_runner for generated adapters (*.g.dart files)
- Excel import: `excel` package + `file_picker`
- OCR: `google_mlkit_text_recognition` + `image_picker` (for photographed/
  screenshotted timetables — "matrix" grid parsing, not general PDF/AI OCR)
- Notifications: `awesome_notifications` + `timezone`
- Calendar: `device_calendar` (native device calendar sync)
- Location: `geolocator` (used for a "proximity to campus" late-trigger
  feature, checked periodically from main.dart)
- Audio: `just_audio` (focus mode ambient/focus sounds)
- Theming: `google_fonts`, `flutter_svg`, custom AppTheme with light/dark mode
- Icons: `flutter_launcher_icons` configured against assets/logo.png

KEY OBSERVATIONS / ARCHITECTURE NOTES
--------------------------------------
- There are two coexisting model/architecture styles: a simpler
  lib/models + lib/services structure (most of the app) and a small
  clean-architecture-flavored lib/data + lib/domain slice specifically for
  the Excel "matrix" timetable import (event_model, student_profile_model,
  import_matrix_timetable use case). This suggests the matrix-import feature
  was built/refactored more recently or by a different pass than the rest.
- Conflict detection is split across three files (conflict_engine,
  conflict_crusher, conflict_service) — worth checking for overlap/duplication
  if working in this area.
- main.dart is doing double duty as both app bootstrap/routing AND the full
  DashboardScreen implementation (over 1000 lines) — a candidate for
  extraction into lib/screens/home_screen.dart-style organization (note:
  lib/screens/home_screen.dart already exists separately, so DashboardScreen
  in main.dart may be legacy/duplicate — worth clarifying before editing).
- Gamification (coins, streaks, streak freezes, milestone badges at 3/7/30/100
  days) is a fully implemented feature, not just in the roadmap — tracked via
  UserProductivity (Hive model) and LocalStorageService.
- Crisis Mode (exam week) is a toggle in the drawer, persisted via
  LocalStorageService.isCrisisMode()/setCrisisMode() — implies some downstream
  behavior (likely more aggressive study reminders) elsewhere in the app.
- Routing is a manual onGenerateRoute switch (no go_router/named nav package),
  with custom transition helpers per route.
- Global error handling is set up in main() (FlutterError.onError and
  PlatformDispatcher.onError) with a fallback error Scaffold if startup fails.

KNOWN ISSUES (verified 2026-08-26 via flutter analyze/test + code reading)
----------------------------------------------------------------------------
`flutter analyze` is clean. Issues found by actually reading service
implementations and their call sites, not just the docs.

FIXED on 2026-08-26 (flutter analyze clean, all 7 tests pass):
1. "Wipe everything" now actually clears all boxes.
   lib/services/local_storage_service.dart clearAllData() now also clears
   courseBox, programBox, productivityBox, and attendanceBox (previously
   only classBox/studyBox/settingsBox).
2. Streak milestone bonus coins (+10 @ 7-day streak, +50 @ 30-day streak) no
   longer lost on restart. updateStreak() now applies the milestone bonus to
   stats.coins BEFORE the single productivityBox.put('stats', stats) call.
3. Attendance record key collisions fixed. markAttendance() now zero-pads
   month/day in the storage key, so e.g. Jan 15 and Nov 5 no longer collide.
   Note: any attendance rows written under the old unpadded keys before this
   fix are orphaned under their old keys (no migration was run).
4. Conflict detection now runs on manual add/edit, not just import.
   lib/screens/edit_event_screen.dart _save() now calls the previously-dead
   ConflictService.findConflicts() against the other stored events and shows
   an "Edit" / "Save Anyway" dialog when there's an overlap.
5. ConflictCrusher no longer misses non-adjacent overlaps.
   lib/services/conflict_crusher.dart detectConflicts() now sweeps with a
   running "active events" list (tracking max end time) per day instead of
   only comparing adjacent pairs after sorting; it also now requires
   dayOfWeek to match (previously ignored day entirely).
6. Reschedule suggestions respect day-of-week.
   lib/screens/conflict_resolution_screen.dart now maps events via the
   existing EventEntity.fromClassEvent (which resolves each event's real
   next occurrence date) instead of stamping everything with "today," and
   searches free slots on the conflicting event's actual day.
7. Notification IDs are now stable, small, and collision-free.
   LocalStorageService.getNotificationBaseId()/releaseNotificationBaseId()
   hand out and persist a small counter-based ID per event (base 10000, step
   10) instead of using event.id.hashCode, which wasn't guaranteed to fit a
   32-bit int or be collision-free. notification_service.dart's schedule/
   cancel calls were updated to use it.
8. Timer leak fixed. main.dart's _ClassTimerProState now stores the 10-min
   GPS proximity Timer.periodic in a field and cancels it in a new
   dispose() override. This was causing a real "Timer is still pending"
   test failure in test/widget_test.dart, which now passes.

Implemented as stubs despite README claims:
- Focus Mode Do Not Disturb: lib/services/focus_mode_service.dart
  startSession/endSession are empty bodies (`// Future:
  flutter_dnd.setDoNotDisturb(true)`) — no real DND/app-blocking occurs.
- PDF import: lib/screens/import_screen.dart:132 shows "PDF support is
  coming soon!" — not implemented.
- Google Calendar two-way sync: only device_calendar (native, one-way push)
  is implemented; no Google OAuth/API integration.
- Cloud backup: settings_screen.dart:382 shows "Backup service coming
  soon."
- Matrix/OCR time parsing heuristic is fragile:
  lib/services/matrix_parser_service.dart:119-129 assumes "hour < 7 means
  PM," silently misconverting legitimate early-morning classes (e.g. a
  6:00 AM class becomes 18:00). Also assumes one fixed grid layout
  (venues as rows, time slots as columns).

GOOGLE PLAY POLICY REVIEW (2026-08-26)
----------------------------------------------------------------------------
Reviewed AndroidManifest.xml permissions, app_store_details.txt disclosure
text, and settings_screen.dart's privacy/parental-gate UI against Play
policy. Fixed:
- Location permission disclosure mismatch: app_store_details.txt and the
  in-app privacy dialog claimed "background location" use, but the app only
  ever requests foreground ACCESS_FINE_LOCATION/ACCESS_COARSE_LOCATION (no
  ACCESS_BACKGROUND_LOCATION is declared or requested). Text corrected to
  accurately describe foreground-only use in both places.
- Non-functional location feature / unjustified permission: LocationService
  used to compare against a hardcoded mock campus coordinate, so the
  location permission was requested for a feature that couldn't work for
  real users. Now: Program (lib/models/program.dart) carries optional
  campusLat/campusLng, set via a new "Use Current Location" action on
  Program Setup (lib/screens/program_setup_screen.dart) that the user
  triggers explicitly while on campus. LocationService.checkProximityToCampus
  now reads the stored campus location and returns immediately (no
  permission prompt, no check) if it hasn't been set — location is never
  touched until the user has opted into a working feature.
- Privacy Policy was gated behind _showParentalGate() (a math-puzzle
  challenge) in settings_screen.dart — removed; privacy policies must stay
  freely accessible. The parental gate is still used for the destructive
  "Clear All Data" action.
- Privacy text overstated calendar sync as "encrypted and sent directly to
  your provider" — corrected to describe what CalendarSyncService actually
  does (writes to the device's own calendar app via device_calendar; no
  servers, no app-level encryption layer).

Still needed before Play submission (not code — Play Console / hosting):

NAVIGATION FIXES (2026-08-26)
----------------------------------------------------------------------------
- Fixed: MaterialApp's default onGenerateInitialRoutes always pushes '/'
  beneath a non-'/' initialRoute (it's built for deep-link paths). This
  silently put Onboarding under Program Setup / Dashboard at startup, so
  pressing back from the first screen you saw landed on Onboarding.
  lib/main.dart now supplies its own onGenerateInitialRoutes that resolves
  only the single requested route.
- Fixed: lib/widgets/event_card.dart pushed a named route '/event-detail'
  that was never registered in main.dart — tapping a card in the
  dashboard's "Today's Schedule" list failed to navigate. Route added; the
  card now also awaits the navigation and calls an onChanged callback so
  the list refreshes after viewing/editing/deleting that event (it
  previously didn't, unlike the "Up Next" cards).
- Fixed: EventDetailScreen's Edit button didn't await the edit screen or
  refresh — since it's a StatelessWidget holding the event it opened with,
  saving an edit left it showing stale data until backing out further. It
  now awaits and pops itself on success.
- Fixed: import_screen.dart's "Confirm & Sync" flow — any class that hit a
  conflict during import went through ConflictResolutionScreen but was then
  never actually saved (an unconditional `continue` skipped the
  addClassEvent call regardless of how the conflict was resolved). Also now
  keeps the running conflict-check state updated so two events within the
  same import batch that overlap each other are caught too.

PERFORMANCE / SMOOTHNESS PASS (2026-08-26)
----------------------------------------------------------------------------

  text (e.g. "Reading your file...", "Detecting the timetable grid...")
  replacing the bare CircularProgressIndicator during import parsing/OCR

  called setState on the whole screen — so typing one character rebuilt

- Hoisted repeated LocalStorageService() reads in main.dart's
  DashboardScreen.build() — getUserProductivity() was being called ~7
  times and isCrisisMode() twice per single build — into one read each,
  reused via local variables.
- Removed unused dependencies from pubspec.yaml: provider, path_provider,
  google_fonts — none were imported anywhere in lib/ (verified via grep).
  Hygiene/build-surface cleanup, not a runtime speedup (unused packages are
  already excluded from the compiled binary by tree-shaking).
- Considered and deliberately skipped: converting the dashboard's

TIMETABLE PROCESSING LATENCY FIX (2026-08-26)
----------------------------------------------------------------------------
Root cause of "processing takes a very long time" (Excel/CSV import path):
lib/services/import_service.dart's parseExcel() called file.readAsBytesSync()
and Excel.decodeBytes(bytes) — both synchronous, CPU-heavy (pure-Dart unzip +
XML parse of the .xlsx) — directly on the main UI isolate. For any real
spreadsheet this fully blocked the UI thread for the whole decode duration:
no frames rendered at all, so even last session's new ProcessingIndicator
spinner froze solid instead of animating, making it look properly hung
rather than just slow. Fixed by running it via compute() (parseExcel is a
pure static function of a File, safe to hand to a background isolate).
Note: parseMatrixExcel (the matrix-Excel import path) has the same
synchronous-decode pattern but was left alone — it also reads
LocalStorageService().getProgram() from Hive inside the function body,
which isn't safely available in a spawned isolate without extra work, and
that path is currently dead code (not wired to any screen, see "Clutter /
dead code" above) so it isn't part of the current complaint.

Also fixed: NotificationService.scheduleClassReminders() awaited up to 4
independent AwesomeNotifications().createNotification() calls sequentially
per class (buffer/15-min/5-min/wrap-up reminders — different notification
IDs, no dependency between them). During "Confirm & Sync" this runs once per
imported class, so it compounded across a whole timetable. Now collects them
into a list and awaits via Future.wait so they run concurrently instead.

Known remaining latency source, not fixed (lower confidence / opt-in only):
CalendarSyncService.syncEvent() calls _calendarPlugin.requestPermissions()
and _calendarPlugin.retrieveCalendars() on every single call, i.e. once per
event during a bulk import — redundant since the resolved calendar/
permission state doesn't change within one sync batch. Only affects users
who've enabled Calendar Sync (off by default). Left alone this pass since
CalendarSyncService isn't a singleton and caching its resolved state safely
(with correct invalidation when the user changes sync provider) needs more
care than the two fixes above; worth doing if calendar-sync users report
slow imports specifically.

"CONFIRM & SYNC" STUCK-FOREVER FIX (2026-08-26)
----------------------------------------------------------------------------
Root cause: lib/services/calendar_sync_service.dart's syncEvent() picked the
target calendar via calendars.data!.firstWhere(..., orElse: () =>
calendars.data!.first) — if the device has zero calendars configured (no
Google/account signed in, common on fresh installs or emulators),
calendars.data! is an empty list and .first throws StateError. This is
called once per class via LocalStorageService.addClassEvent() inside
import_screen.dart's "Confirm & Sync" loop, which had NO try/catch anywhere
in the chain — an unhandled exception here silently killed the async
handler mid-batch, leaving _isLoading stuck at true forever: spinner
showing, no error, no navigation, no way out. (Only reachable if the user
has Calendar Sync enabled — off by default — but a real, reproducible dead
end when it applies.)

Fixed at both levels:
- calendar_sync_service.dart: guard for calendars.data!.isEmpty and return
  early instead of crashing.
- import_screen.dart's "Confirm & Sync" handler: wrapped in try/finally so
  _isLoading always gets reset no matter what throws, and wrapped each
  per-event save in its own try/catch so one bad class (malformed data, a
  plugin failure, anything unforeseen) can't take down the whole batch —
  it's now skipped and reported by name in the completion SnackBar instead
  of hanging the screen.

TIMETABLE PROCESSING BROUGHT IN LINE WITH logic_and_algorithm.txt (2026-08-26)
----------------------------------------------------------------------------
The doc's Universal Import Engine section describes two things the actual
code didn't do yet — implemented both, in lib/services/import_service.dart:

1. Excel/CSV "Mapping: Detects headers (Day, Subject, Start Time, End Time)
   and maps column data to Structured Event objects." parseExcel() used to
   hardcode column positions (row[0]=day, row[1]=title, ... — the code
   literally said "// Basic header detection (future: dynamic mapping)").
   Added _detectColumnMapping(): scans the first 5 rows for a header row,
   matches each cell's text against keyword lists (day/weekday,
   subject|course|class|title|unit|name, start|from|begin, end|to|finish,
   venue|room|location|hall) in any order/position, and maps columns by
   name. Falls back to the old fixed Day|Subject|Start|End|Venue layout if
   no header row is recognized, so already-correctly-ordered files still
   work unchanged.

2. OCR "Heuristic Association: Associates text blocks (Course Names) found
   immediately near detected time ranges with those specific events."
   reconstructFromOCR() (renamed from _reconstructFromOCR — Dart privacy is
   per-file, made public so it's unit-testable) used to only find a title
   by stripping the time range out of the SAME text block — meaning a
   timetable screenshot where ML Kit recognizes the course name and its
   time as two separate blocks (very common for grid/table screenshots)
   produced a class with no title at all. Now does two passes: classify
   every block as a day header / time-range (with optional inline title) /
   title candidate, then for every time range without an inline title,
   associate the spatially nearest unclaimed title-candidate block by
   bounding-box center distance, capped at 3x the time block's own height
   so it won't grab an unrelated block on a sparse image.

Both are covered by test/import_service_test.dart (5 new tests: header
mapping in non-standard column order, fallback to fixed layout, OCR
cross-block association, the original same-block case still working, and
a control case confirming a too-far-away block is correctly NOT
associated). TextBlock/RecognizedText from google_mlkit_text_recognition
have public constructors, so these are constructed directly rather than
mocked. Full suite: 12/12 passing, flutter analyze clean.
